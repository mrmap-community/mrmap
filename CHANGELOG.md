## [0.x.x] - UNRELEASED

### Added
- Every read of a WMS or WFS answers `visibility` - `public`, `organization-internal` or `restricted` - derived from the guardian grants themselves instead of stored beside them, so the list, the detail route and the permission checks can no longer answer three different versions of "who may see this" for one resource (#739, the split #727 called the bug). Public means an explicit `view` grant onto the new platform role group `anonymous_viewer` - seeded by a migration, guarded on `post_migrate`, with guardian's anonymous user as its only member and nothing else ever joining it - so every newly registered resource starts organization-internal by construction and only publishing makes it public (decision Q2 of #727); a public resource reads public for logged-in callers too. A `PATCH` moves a resource across the public axis, gated on `registry.publish_resource` for the way out and on that or `manage_access_rules` for the way back; `restricted` is answered but never writable - shaping it is #740's sharing. On a list the tri-state is one `CASE` over two `EXISTS` in the page's own SELECT: no query per row, none per role. Which lists are actually *filtered* to what the caller may view is a per-model rollout switch (`MRMAP_PERMISSION_FILTERED_LIST_MODELS`, default empty = today's answer everywhere, `accounts.E006` refusing any model the role system does not manage), and switching it on decides list, detail and count by the very `objects_for_user` SQL of #734 - rollback is the empty value.
- Cross-service attention list, app-bar count and dashboard card for service failures, update reviews and overdue schedules (#567).
- Alerts of a service answer which monitoring run, update job or harvesting job decided them, and the attention tab of a service links to that record (#596).
- The aside of a screen of services answers the selected service first: its states which need attention, the outcome of its last monitoring run and update job and a direct way to its screen (#597).
- Work queue card on the dashboard which counts the alerts, the update reviews and the running and failed background work of everything the user may see, and links to the list of those very records (#601).
- The capabilities document of a stored WMS or WFS publishes the dataset coupling a curator maintains in MrMap: a curated relation of a layer or feature type adds a metadata reference which points to the iso record of the linked dataset, beside the references which were imported with the document (#674).
- The step size a harvesting run requests pages with is a size a run can carry and the catalogue keeps it: a run which names no size starts from the size of its catalogue, a run which finished leaves the size it worked with there, and a size which no run can carry is answered as invalid input instead of breaking the run or the request (#691).
- A harvesting run finds the page size the catalogue answers instead of trusting a default nobody chose: the size is probed with a request which asks for no records, halved until the service answers it, and a page which is refused at the planned size asks its missing range again in halved steps down to a floor - every size used and every shrink is readable in the harvesting logs, and the request timeout grows with the page size so a slow page is not mistaken for a broken one (#694).
- A harvesting schedule which fires more often than a harvest of the catalogue takes asks for attention: the warning names the schedule and the duration the harvests which finished measured on average, is answered on the harvesting schedules of the catalogue and in the attention list, and never blocks saving such a schedule, because the duration of a harvest drifts with the remote catalogue (#693).
- The harvests a catalogue already had behind it answer how fast every page size is: a harvesting run which completed answers its records per minute beside the size it asked with, the size a harvest starts with is shown together with the throughput the runs of that catalogue measured per size and the fastest one of them, and a catalogue whose harvests never finished is shown without a recommendation instead of a made-up one (#692).
- Per layer opacity in the map viewer: the layer settings panel blends a layer between invisible and fully drawn in five percent steps, keeps the value for the viewer session, and asks for a map of its own as soon as two layers differ, so the blending of one layer never dims another; a feature layer dims its outlines, fills and point symbols together (#750).
- The map keeps its image while the time dimension of a WMS is scrubbed or played: the frame already drawn stays visible until the frame of a new selection is fetched, decoded and ready, the control names the observation the map shows while its successor is on its way, and identify asks that shown frame; the time control animates the advertised times from their first value with play/pause, four playback speeds and looping, holds its pace while a frame is on its way, steps over frames the service refuses, and stops at the end of the range unless looping was asked for (#705).
- The frames which follow a time selection are fetched before the user reaches them: while the timeline of a layer is open the viewer buffers the next advertised observations in the background and draws a buffered frame without asking the service again, at most two buffered frames are on their way at once, the frames a selection moved away from are taken back together with the requests still travelling for them, a layer whose timeline nobody opened and the image of the server default are left alone, and a buffered frame never answers a layer asked with different credentials (#705).
- The capabilities of a single layer or feature type have an url of their own - `/mrmap-proxy/wms/layer/{layer}` and `/mrmap-proxy/wfs/featuretype/{feature type}` - which the api names on the layer and on the feature type: the document is generated for every request out of the registry and advertises exactly that resource, writes what a nested layer inherits from its parents into the layer itself so the document answers it without the parents and restricts the type names a WFS advertises, so a viewer can be pointed at one element, while a wrong version, an unknown resource or an ambiguous identifier is answered with an exception report instead of a document; the inspection of a layer or feature type shows the recent changes of the inspected element alone (#676).
- The screens which list the registered layers and feature types open the element their user clicked in the map viewer: the card beside their rows names the service which owns that element and hands both to the buttons which open the service in the viewer, so the viewer shows the capabilities of the whole service with exactly the clicked layer or feature type activated - a secured service is opened with its secured document, a feature type is asked alone instead of offering every type of the service for the choice the click already made, and the operations a document of the registry advertises on another origin are asked upstream without the session of the requester (#676).
- Errors of the user's browser reach the central logs: a beacon script which the frontend image injects before the app bundle reports uncaught exceptions, unhandled rejections and failed resource loads to `/api/system/error`, an url the frontend's own nginx answers without the backend involved - the fields travel in the query string so one report is one line of a log of its own which ships with the container logs like the access log, its values arrive as they were sent, the address is bounded by a rate limit instead of by credentials, and the access and error logs of the frontend container join the log stack (#889).
- The diagnostics of a harvesting run answer what the run measures about its own work: the tab shows the download and the database duration its records carried, how long the run has been working - the moment the run was made is read from its change log, because the harvesting never wrote a creation date - and how many records per minute it has stored so far, beside an estimated remaining time and the moment the run is expected to end; the estimate is worded as an estimate and is answered for no run whose records are not known yet, whose progress is nothing or which is closed, the numbers travel with the websocket message of the run so they do not empty on the screen with the first push, and the summary card reads the elapsed time from the api instead of deriving it in the browser: none of these answers aggregates the harvested metadata relations - what a run has stored comes from the count of its own temporary files and from its steps, and the measured durations of one run now read the records of exactly that run - because the screen which shows them polls every few seconds while the import of this very run is writing into that table (#1071).
- A list which declares a default column that the schema of its resource does not answer names the mismatch on the console of a development build, with the resource and the key: such a column renders nothing for every record, which is how a catalogue's harvesting tab carried an empty creation-time column for ages because it asked `createdAt` while the api answers `dateCreated` (#1078).
- A run which left records behind leads the way to them: the new tab "Records it could not store" names the files whose import the run refused - request, page, refusal and duration as declared columns - and what became of the records it did read, with a link from every relation row to the record it made; the new "Log" tab lists the run's log lines in the order of their own timestamps, narrows them with a level facet to info and above or warnings and above and shows the log level of the run beside them, and says per line whether a stored response hangs behind it, which the list never fetches for every row - only the detail of the one line reads it; the counts of unhandled and refused records become links into these tabs, the log tab stays absent for a caller the api denies the lines while the counts remain, and neither of the two lists gets a menu entry, a column chooser or an export, because a global pile of every log line is what #888 is about (#1083).

- Two branches which each add a migration of the same number stop costing a merge-queue cycle: `scripts/migration_graph_smoke.py` reads the migration files of `HEAD` and of `origin/master` with `ast`, asserts that the graph of their union still has one leaf per app and names both leaves, the file declaring each and the side it comes from - so the pair of `0038`s PR #1114 and PR #1145 both brought is answered in a fifth of a second at push time instead of by the queue's `makemigrations --check` seven minutes later (host Python plus the `git` CLI: no docker, no `gh`, no network; offline checks in `scripts/test_migration_graph_smoke.py`, #1157).
- A service whose update job stands undriven gets its schedule back: the hourly sweep `registry.tasks.update.sweep_stale_update_jobs` fails unfinished service-update jobs of every kind which stood in a not-yet-decided state - waiting for processing, updating or resumed - beyond a configurable horizon (`MRMAP_UPDATE_JOB_STALE_HORIZON_HOURS`, default 24 h), because a delivery which is gone for good (a broker recreated with the database kept, a purge, a discard) or a run whose retries died without the job ever deciding leaves the job unfinished, and the constraint of one unfinished job per service makes every later fire of that service's schedule re-use it without enqueueing anything - the service is then never updated again, silently, forever (#1460). Each decision happens under the same row lock the runners of #1453 hold, so a job a worker takes at this very moment is never decided twice, and the horizon - which no legitimate update run outruns - is what tells a job which still works from one nobody drives. A mapping which waits for a human review and a run which decided its outcome while only its metadata step is open are left alone; the recovery of #1274 and #1263 owns those. Every decided service is told to the incident channel of #1319 as a watchdog verdict which the service's next completed update resolves, the sweep's decision is logged on the background process and the schedule creates a fresh job for the freed service again (#1460).

- The role system explains itself: the catalogue of role definitions, the roles of an organization and their memberships are audited, their changelogs answer under `/api/accounts/historical-roledefinitions`, `/historical-roles` and `/historical-memberships` with the very permission class of the resource each trails, and the roles and members screens of the administration link them in their toolbar - who made a role, who retired it, who granted a role to whom and who took it back again, with the grantor and the validity read off the row which decided it. A permission decision is explained by `GET /api/accounts/effective-permissions` for the calling account: it names the layer which decided (`break_glass_superuser`, `object_grant`, `public_object_grant`, `platform_role`, `organization_role`) and the concrete grant behind it - the guardian row with who wrote it, or the membership with its role, organization, grantor and `valid_until` - because #734 answers *whether* and this answers *why*. The explanation walks the same axes in the same order through the same functions as the decision, so the two cannot drift apart, and it decides nothing of its own; a retired *global* grant of a pre-role deployment is reported as observed and marked as what the migration maps onto roles, never as a decider. The answer is about its caller only - an unrelated caller is refused and nothing is listable - while the administrator of an organization, or the platform holder, may ask the same question of another account over an object of their organization (#741).
- A role membership whose `valid_until` has passed stops granting by itself: `accounts.tasks.revoke_expired_role_memberships` deletes those memberships on the celery db queue once an hour - a periodic row created on `post_migrate`, a singleton so two runs never overlap - which takes the user out of the group of the role and thereby revokes every guardian grant that group gave them. Until now an expired membership stopped the role axes of #734 while the grants of the group still reached the person, so whether she could still publish depended on which path asked; the deletion names its reason in the change log, so an audit tells an expiry apart from a revocation by a person (#741).
### Changed
- The epic #1408 candidate "batch WFS DescribeFeatureType" (#1414) lands as a verdict, not a code change: the per-type fetch chain - `FeatureType.fetch_describe_feature_type_document`, its `parse`/`create_element_instances` downstream and `WebFeatureServiceClient.describe_feature_type_request` - has **no production consumer today**. The task that looped feature types and paid one DescribeFeatureType request per type (`create_feature_type_elements`) was removed in `6b3110891` (2021) and never replaced; operator commands, scripts, monitoring, harvest, preview, the proxy and the API were all traced and ask none (the proxy only forwards a client's own DescribeFeatureType), so batching would have saved 0 requests - the repetition the issue itself demands before batching is not demonstrable. The trace corrected audit finding R6 beside it: `FeatureTypeProperty` rows do not come from the capabilities config - the describe config's mapping is their only writer, reachable only through the unconnected chain - so production stores no properties at all, and both readers (the security annotation's `Coalesce(..., "THE_GEOM")` fallback, the GML preview's `None` tie-breaker) degrade empty by design; wiring a describe fetch back in would change secured and previewed behaviour and is a product decision. The evidence, the conditions that would re-open batching and the requirements then binding (multi-typeName compatibility with bounded, fallback-capable requests, namespace and import mapping back per feature type, per-type failure handling, no sharing across auth/version/scope) are recorded in `docs/source/development/wfs-describe-batching-verdict.rst`, and the call-path fixture the audit named as missing is `tests/django/registry/models/tests_describe_call_path.py`, which fails when any production module reaches the chain. No runtime behavior changed.
- An imported ISO document is transformed as often as it is imported, not more: `MDMetadataXmlMapper.from_xml` copied every `MD_Metadata` node through `tostring` and `fromstring` so each mapper could hold a standalone document, which for the node that *is* the document root - the shape every store path produces, because a CSW page answer is cut into one file per record, a filesystem import stores the parsed node and a registration downloads the advertised document - only paid for a structurally identical tree, so the copy now runs only for a node which must be cut out of a bigger document. The whole-document backup of the record was serialized by every persistence call *before* it knew whether the catalogue's answer changed anything: an unchanged re-harvest, or the ninth reference coupling to one already imported document (#1410), paid a full serialization for a backup nobody wrote; it is serialized when a record is written and shared by the records of one document. The post-filter of the application bucket (#827) traversed the `hierarchyLevel` a second time right after the mapping had answered it to select the mapping config, which the mapper carries with it now. And the parsed instances of an import are released from the process-global cache when its import is through instead of being held until the TTL of #1028, which on a harvest worker was a parsed copy of the backlog it just worked through. None of this touches the write cadence of #858, the bulk lookup writes of #817 or the bounded import chunks of #859: one record is still written once, and the mapping of a repeated *shared reference* stays per delivery, because no cross-run cache may grow there. What the stages cost, what was reviewed and deliberately left alone (the two keyword-quality evaluations of #919, the handler per mapped instance) and which findings are database-side questions of #1392 is inventoried in `docs/source/development/metadata-transform-inventory.rst`; `tests/django/registry/mappers/tests_transform_counts.py` counts the transformations at the seams they happen at (#1415).
- The browser authenticates with a Django session instead of a token it holds itself (accepted decision Q8=B): `POST /api/auth/session` turns the Basic credentials of the login into a session whose `HttpOnly`, `SameSite=Lax` cookie the browser attaches on its own - nothing in the answer is a credential to copy out of a script-readable response or to put into a WebSocket URL; `GET` probes whether the cookie still authenticates (and thereby bootstraps the CSRF cookie), `DELETE` flushes the session server-side. The SPA repeats the `csrftoken` cookie in the `X-CSRFToken` header of every state-changing call (axios and the provider's own fetches), the websocket handshake is same-origin so `channels` resolves the user from the session cookie, and what survives in `localStorage` is an identity marker only. A page load finds the knox token the previous frontend left behind, revokes exactly that token at the still-mounted `POST /api/auth/logout` and drops it; the knox endpoints stay as the credential path of scripts and CLI clients, and a rollback to a pre-#835 frontend stays possible (the policy and the rollout are documented in `docs/source/administration/authentication.md`) (#835).
- The same ISO document advertised by many references is pulled once per collection run instead of once per reference: the plan of a registration now writes one `RegistrationDocumentAcquisition` row per distinct advertised url beside the reference rows, which carries the fetch lease and one stored copy of the document; the delivery which wins that claim fetches, every other reference of that identity waits, copies the bytes into its own file under its own claim token and imports them - each reference still keeps its own outcome, counters, failure kind and retry identity (#1263). A fetch whose attempts ran out or which answered without a document decides every reference still waiting on it at once, while the acquisition row itself stays open for the retry API of #1265; a fetch lease whose holder died is taken over by a waiting reference, and the completion of the run waits while a fetch is leased. No url normalization joins queries: a different advertised query stays a different acquisition with its own request, and the acquisition key carries nothing a reference could leak (#1410).
- Which rows a list of resources answers is declared by the resource, not guessed by the screen: the filter which hid update candidates from the lists of WMS, WFS, layer and feature type moved out of `ListGuesser` into the four resource definitions, which declare it as `options.list.filter: { is_update_candidate: false }` now - the same filter parameter on the same four requests, because all four api filtersets answer that filter, and a definition which declares its own filter keeps it while the guesser adds nothing. Reading the nested operations of the api is the OpenAPI parser's job too: `getRelatedResourceType` is the one reader of the shape the schema nests them in, so the related routes of the app shell are built from the same read as everything else derived from the schema, and an operation the schema does not describe is left out instead of being routed to `undefined` (#1467).
- Screens stop rebuilding the world after a write: the buttons which mutate through react-admin's `useUpdate` or `useCreate` answer their mutation with no `useRefresh` of their own any more - the hooks already invalidate the record and list queries of the resource they mutate, so what was left was a reload of every query the user has cached, unrelated ones included; where a control changes data another resource shows (assigning a role moves the role chips of the member list, which the User list answers per row), it invalidates exactly that collection now (#1464).
- Polling which the realtime bus can answer waits for the bus: the alerts list, the alerts count hook, a catalogue's harvesting runs tab and its activity card re-ask only while the websocket is not open (their `refetchInterval` is gated on `realtimeIsReady`), and the activity card subscribes to the live topic like the run list beside it. The attention tab of a service moves its minute re-read out of a `setInterval` of its own into the record query of the show screen, which TanStack pauses in a hidden tab and which refreshes every record-derived view, not the tab alone. The intervals without a live counterpart stay: update jobs, monitoring runs and harvesting schedules have no bus topic - the backend broadcasts `BackgroundProcess`, `HarvestingJob` and `ServiceAlert` only - so gating them would freeze their progress read-outs while the bus is healthy, which is how far this issue's premise reached (#1464).
- **Breaking:** the permission hints of the api are one field now: `allowedActions` lists the actions the requesting user may take on a resource - `view`, `change`, `delete` and, where the app declares them, `publish`, `share` and `manage_access_rules` - answered by the permission facade of #734, so the hint and the endpoint which enforces the write can no longer disagree. The retired `canEdit`, `canDelete` and `isAccessible` attributes are removed from every service and record representation; a client reading them must read `allowedActions` and ask it for the action it cares about (`allowedActions.includes("change")` replaces `canEdit`). As the retired `canEdit` on lists, the field answers only where a sparse fieldset names it on a list, and unasked on a detail. The UI gates its edit, delete and editor screens on the same field (#738).
- **Breaking:** registering a WMS, WFS or CSW is followed on its `BackgroundProcess` now: the HTTP 202 of the registration POST answers that resource - correctly typed, with a `Content-Location` pointing at `/api/notify/background-processes/<id>` - instead of a `TaskResult`, and it leaves no row of the legacy table behind. Polling the process alone answers the queued, running and terminal states, names the service as soon as it exists and carries failed metadata steps in its logs; its `completed` means the whole workflow ran to the end, including the requested metadata collection, which is when the service built earlier may still watch its records arrive. The `task-results` endpoint stays readable for the rows of the time before this cutover, and retiring it follows the accepted boundary of D01/B of #1175 - the release which carries the removal is to be named by a maintainer (#1177).
- The list of harvesting runs is an explicit screen now: the phase of every run with its progress, throughput, running time and number of records is spelled out per row, the columns are fixed, and unfinished runs can be stopped one by one or in bulk. The page heading names the runs "Datenübernahmen". (#1087)
- One request no longer inflates the latency of its unrelated neighbours: the HTTP of the `backend` container is served by sync `gthread` workers of the WSGI application instead of ASGI workers of the ASGI one, because every view of MrMap is sync and an ASGI worker makes them share one GIL with the event loop which keeps their sockets - measured behind a 4-core quota with 4 workers and a burst of 8 `/api/schema` builds, the ASGI configuration used 1.8 - 2.2 of the 4 cores and answered an idle-server-5 ms neighbour only after 181 - 233 ms, the `gthread` configuration 2.7 - 3.4 cores and 41 - 95 ms; the websockets, which are the one part of the app that has to be ASGI, keep an event loop of their own on port 8002, the edge of the frontend forwards `/ws` there, `GUNICORN_THREADS` sizes the queueing depth of one HTTP worker, and `docs/source/development/environment.rst` carries the whole reading (#1032).
- The first boot of the web app travels lighter: the nginx of the frontend image compresses the answers it serves itself, lets the hashed files under `/assets/` be cached immutably and keeps the html uncached, and `/api/schema` answers with a strong ETag, a public cache directive and a `Vary` without credentials, so a reload of the app asks for the multi-megabyte schema document only to learn that nothing changed and downloads it in full once per cache period instead of once per boot (#946).
- The system status of the app bar stops polling `/api/system/status/current` while the MrMap tab is hidden and refreshes the displayed status as soon as the user returns (#749).
- The browsable REST API is a development facility only; a production deployment (`MRMAP_PRODUCTION=True`) registers no browsable renderer, so an HTML-only request is answered with the usual content negotiation rejection and requests without an `Accept` header receive the JSON:API representation (#751).
- A metadata reference of an imported capabilities document is published as it was imported and is removed only if the database does not know its link anymore; a reference which holds no online resource is no longer published, because it is not valid xml (#674).
- building docs with readthedocs.org instead of using custom github action to publish with github pages.
- Importing one harvested metadata record writes its row once instead of up to three times: the xml backup of the document and the reason of its history row travel with that one statement, a record which the catalogue did not change is not written at all, and a harvest no longer answers `is_customized` of a record it only re-harvested (#858).
- The import which writes harvested records to the database is bounded by chunks instead of one task per record: a harvest of 70,000 records publishes ~280 tasks (`MRMAP_HARVEST_IMPORT_BATCH_SIZE`, 250 by default) instead of 70,000 broker messages, task round-trips and result writes, and the directory import of stored files is bounded the same way; every record still commits on its own, keeps its own documented import error without failing the chunk it sits in, and is skipped as already imported when its chunk is delivered again, while the progress a harvest reports stays granular by record (#859).
- The history chart of a resource counts the changes per day of the last 30 days as stacked bars of the additions, the updates and the deletions, draws the inventory as a line above them and names the time, the unit and the resource it counts in a caption; a resource which answers no statistics, a request which is still asked and a request which failed are told apart from a resource without any change (#601).
- `scripts/agent_capacity` measures the memory of the cgroup an agent actually runs in instead of the machine's: a job is admitted against the smaller of `MemAvailable` and the headroom of its own cgroup and every parent, counting only what cannot be reclaimed, it distinguishes a heavy Compose test stack from a light agent slot, counts stacks and processes prospectively so `stacks 3 (max 3)` no longer admits a fourth, and refuses a new stack under memory pressure or at the cgroup ceiling without ever touching a running job - the 16 GiB agent container whose 11 OOM kills the 2026-11-05 diagnosis recorded is now seen as 16 GiB instead of the 63 GiB `/proc/meminfo` reports; thresholds, metrics and the measured before/after are in `docs/source/development/agent-capacity.rst` (#1053).
- The unit-test job runs its suite in four forked workers instead of one process: the 1312 tests of `tests/django` measured 655 s in a single process and 225 s with `--parallel=4` in the same stack, and the peak of the container's memory cgroup did not rise with them (12.1 against 12.5 GiB), while the worker count is written out rather than left to the runner's `cpu_count` because Django brings up one PostGIS test database per worker; `COVERAGE_FILE` and `concurrency = multiprocessing` travel with the switch because a forked worker inherits the environment of its parent but not its command line, so without either one the job uploads a coverage report that silently lacks every line only a worker executed and still exits 0 - `scripts/test_coverage_parallel_data.py` pins that together with the single-process shape of the acceptance job, and `backend/AGENTS.md` now carries the measured numbers in place of a baseline that no longer described this suite (#1055).
- The read plan of the monitoring and the service-update Celery tasks is their own now: the by-pk probe fetch of `run_probe_check` carries its setting, service and authentication in one SELECT and reads the scoped layers once, the probe row is no longer saved per check, and the old and the new service of an update job read exactly the relations their update config names instead of the whole UI plan - the configured element relations ride the mapping read, so a 100-layer update costs the same statements as a 1-layer one (#1393).
- **Breaking:** the groups and the organizations of the api are guarded like its users now, and the members of a group are no longer writable over the group: both viewsets named no permission class at all, so an anonymous `PATCH` of `relationships.users` of a group was answered - and object permissions are granted to the role groups of the organizations (#732), while an `Organization` *is* its group row, so that one document joined any organization and took what its roles may do. Both endpoints now ask `DjangoObjectPermissions` like `UserViewSet` does: reading needs an identity (an anonymous client is answered 403 `not_authenticated` where it was answered the rows before), writing is asked as the model permission *and* as the grant on that very object. The relation stays answered and becomes read-only, because the sanctioned way in exists since #736 and fails closed: `POST /organizations/{id}/members` for the organization the caller administers, the role memberships for a role; the administration screen of #737 uses those, the plain group write is retired by #741. Writing the members of an organization's or a group's row is therefore an act of a global grant (today: the break-glass account), exactly as changing a user is, and a client which still sends the relation with a `PATCH` has it ignored rather than written. A page of groups reads its members with one statement instead of one per row (#1448).

- An update which adopted a document leaves the service *stored* as that document: `adopt_stored_document` writes the raw capabilities answer this run compared against into the `xml_backup_file` of the service, under the name the file already had, so `document_equals`, the stored capabilities read of #1044 and the integrity check of #1150 all answer the state the update published. Only registration wrote that file before, so after the first real change the stored document kept showing the registration and every later cycle of a settled service proved *changed* again - fetch, parse, map and persist a whole candidate, delete it, collect the references of the registration - forever; the settled cycle now costs one capabilities request and zero candidate parses, which `tests/django/registry/models/tests_update_refresh_policy.py` pins with a `Session.send` side_effect which runs out on any request the flow should not make and a patched `OGCServiceXmlMapper.from_xml`. Adoption moves the advertised ISO references of the adopted document onto the published service and its elements as well (`_republish_references`): the rows the candidate carried describe the published elements, links the new document does not advertise are taken back in the same statement the rows of the removed elements go, and the metadata step of #1274 collects what the service advertises *now* instead of the stale list of the registration - records found through a dropped link stay registered and the supersede bookkeeping of #1261 answers their relations, as it does for every link which resolves elsewhere. Which work an update may skip and which it must redo - among it that capabilities equality never skips revalidating the advertised documents, because the hash proves the capabilities and nothing about the ISO records behind them - is the decision table of `docs/source/development/update-metadata-refresh-policy.rst`; the second delete sanctioned on one fingerprint in `tests_task_sql_update` is this take-back beside the candidate deletion's own cascade, still constant over the pairs (#1413). The CSW update path keeps its own copy of the defect and is untouched here, documented as open in that page.
- Which COUNT a paged list pays for its annotations was measured and is now pinned (#1478): the audit feared the paginator's COUNT re-executes the alert derivation. It does not - displaying, sorting or searching a list of services keeps the monitoring-run and update-job subqueries out of the COUNT entirely (`QuerySet.count` drops the SELECT annotations, the page-bound counterpart of #1424), the one filter whose meaning IS the derivation (`filter[has_alert]`) asks it as exactly one COUNT, and the cross-service alert list reads the stored projection of the rules (#1030), so no derivation is there to re-execute either; a cached count (#885) would answer none of these. The metadata relation search does COUNT over its five title joins - measured to be five primary-key joins, so one COUNT plus at most one page without fan-out and without DISTINCT, and an EXISTS rewrite would cost the same by construction; vectorizing the search stays scale work for #1424/#1426. And `ServiceHistoricalRecords`, which decides per audit row of every element whether its service is an update candidate, asked `instance.service` - a full-row read of the service per element, even when the caller already held it: a held service is answered from the field cache without any query, the cold path asks for the one column as a single-column EXISTS, and the SQL guard of the update apply phase re-pinned its per-pair attribution fingerprint to the narrower statement (the two constant deferred FK reads of the job's own diff plan, previously hidden inside the old wide fingerprint, are sanctioned by name). The stale-relation take-back `drop_superseded_relations_for_link` loaded every superseded record whole and DELETEd its couplings one statement per record; all superseded records share the class of the created one, so the columns are identical and one aggregate DELETE now closes the whole (describes, origin) pair - pinned through two generations of republishing. No schema change; new `tests_save_write_costs.py` pins the SQL shapes and the unchanged outcomes, the collection module pins the one DELETE over two stale records, and the update module's scaling guard keeps its one-statement-per-pair verdict on the narrowed read (#1482).
- `scripts/mcp-setup.sh` no longer costs a host its own OpenCode configuration: its last step wrote `.opencode/opencode.json` out of a heredoc, and that file is the *local* layer of the host's config - the model and provider selection, the context and output limits of a locally served model, compaction, permissions and the MCP servers someone switched off on purpose all live there - so one run of the setup script discarded them, and the hot reload which followed brought the disabled servers back and read the context limit as the provider default instead of the configured 32K (#1637, seen during a run of #1434). Step 4 now delegates to `scripts/mcp_config_merge.py`, which replaces `mcp.servers.postgres` and nothing else, carries every other setting over - other servers *with* their `disabled` flags, the `mcp` settings beside `servers`, keys OpenCode does not know yet, the host's own `$comment` - and validates before it touches anything: a config it cannot preserve (invalid JSON, a JSONC comment or a trailing comma, a top level or an `mcp`/`mcp.servers` which is not an object) is refused with exit 2 and stays byte for byte as it is, so a local file the script cannot read fails the step instead of silently being replaced. The write is an atomic `os.replace` of a temp file created 0600 - a file holding a DSN is not world-readable even briefly, and one left at 0644 is tightened - and the DSN reaches the merger on **stdin**, never as an argument (which `ps` would show) and never inside a message. `MRMAP_MCP_NO_DB=1` still skips the DB steps and leaves an existing override untouched. `python3 scripts/test_mcp_config_merge.py` pins all of it offline: merges into temp directories with synthetic credentials, and real runs of the script against a throw-away checkout in the same temp tree with `git`, `docker`, `openssl` and `gh` stubbed - so the check which fails the heredoc version is proven without a container, a database, the host's config or a credential that could be printed (#1637).
- The service alerts only hear real harvesting state transitions: the `post_save` receiver of `HarvestingJob` invalidated the stored alerts on *every* save - the plan and progress saves of the tasks included, which write `total_records`, the step size or the bookkeeping of the watchdog - while the harvest alert reads only three facts off a run: that it is the newest of its catalogue, its phase, and its completion (`annotate_harvest_alerts`); what a run left its records behind in travels with the record rows and the log lines and never with a save of the job. A working harvest therefore published the invalidation message and enqueued the rewrite of the whole alert table per save, for a state no alert could answer differently with. The receiver now invalidates on the creation (a new run is the newest), on the saves which write the change log of the run (the workflow's own convention: `skip_history_when_saving=False`, and the branches of `HarvestingJob.save` which decide about the run never carry the skip), and on a save which finds the run done or aborted - while the websocket push of the run itself stays one per save, which is what the run screen reads its progress from. `test_harvesting_signals.py` pins both halves - a progress save which invalidates nothing and still pushes, and the transition saves which speak to the alerts - and the alerts' delivery test keeps its verdict (#1485).
- One dataset record is coupled to one element once: the pairs of the service side of `MetadataRelation` have been UNIQUE-indexed since its first migration, the dataset side never were - and `add_metadata_relation` asserts a coupling with `get_or_create` inside `select_for_update`, which locks a row that exists and nothing at all for a missing one, so two writers of one couple (the same reference collected twice, a registration beside an update) both saw no row and both wrote one. The four declarations of Django's deprecated `unique_together` this project owns are `UniqueConstraint`s with a name of their own now - the three `*KeywordsLink` tables and `PublishRequest` - and `registry/0061_…` plus `accounts/0013_…` rename the indexes which already existed in place with `SeparateDatabaseAndState` and `ALTER TABLE … RENAME CONSTRAINT`: Django 6.0 has no `RenameConstraint` operation, and the drop-and-rebuild `makemigrations` generates would rebuild a unique index that only needed a name. New `tests/django/registry/models/tests_dataset_coupling_uniqueness.py` answers the schema per kind of coupling and travels the `MigrationExecutor` through the upgrade, so the dedupe is tested against the schema which allowed the repetitions (#1483).
