Design intent. The list answers one question per row: what is this run doing, how far is it, and when will it be through. Everything in it comes from fields the harvesting-jobs endpoint already answers — phaseLabel, progress, doneSteps/totalSteps, totalRecords, unhandledRecordsCount, importErrorCount, doneAt — named in the sparse fieldset of the request, so a screen never pays for a column it does not show. Columns are declared explicitly and the column chooser is switched off, exactly as the registered-services list does it.

What the api has to answer first. Throughput and time left of a running run are #1071 — recordsPerMinute deliberately stays empty for a run which did not finish, and an estimate must not re-aggregate the harvest the screen is polling (#1037). Elapsed time is #1071 as well: dateCreated is empty for a run the harvesting made, so the moment a run was made is read from its change log. Phase facets and the catalogue title search need filters the filterset does not have yet (service__id, id, is_unready are all there is).

What stays empty on purpose. A run which is still counting records, or one which is queued, has measured nothing and answers no time left. An aborted or completed run has nothing left to estimate, is not selectable and has no stop button — only a new harvest. A stop is the mutation the show screen already sends: PATCH phase = 4711, shown only while doneAt is empty and only to a user allowed to change the run.
