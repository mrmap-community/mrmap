.. _release-compatibility-gates:

===========================================
Release compatibility and upgrade gates
===========================================

.. sidebar:: Issue #1583

   Part of epic #1577 (release management), issue #1583: the quality gates a
   release candidate passes on its public contract, its migrations and its
   promotion evidence. The gate tool is ``scripts/release_gates.py``; the
   baseline audit it builds on is :ref:`release-versioning-baseline` (#1578),
   the version identity is :ref:`canonical-version` (#1579), the change
   classification is ``scripts/pr_classify`` (#1580) and the artifact identity
   is :ref:`versioned-images` (#1582).

What this is, in one line
=========================

Four gates that decide - offline, on the host, against reviewed baselines -
whether a candidate may be called a release: the **contract diff** against the
previous supported stable release, the **version bump** and migration notes
the range owes, the **upgrade surface** (graph, #1180 boundaries, fake and
destructive migrations), and the **promotion attestation** that binds a
candidate SHA to its evidence. Nothing here approves, merges, tags or
publishes anything; a gate says ok, FAIL or *cannot run*, and a human owns the
decision.

Run them
========

.. code:: console

    $ python3 scripts/release_gates.py api      --candidate backend/openapi-candidate.json
    $ python3 scripts/release_gates.py version
    $ python3 scripts/release_gates.py upgrade
    $ python3 scripts/release_gates.py promote  --evidence evidence.json --gate api=api.json ...

Exit codes are those of every tool in ``scripts/``: **0** pass, **1** the gate
decides against the candidate, **2** the gate could not run and refuses to
pretend otherwise. CI runs the three candidate gates on every pull request,
merge-queue entry and develop/master push in
``.github/workflows/release-gates.yml``; the offline suite
``scripts/test_release_gates.py`` (51 checks) runs in
``scripts/check_repo_tooling.sh`` and drives each gate red with its intentional
failure and green with the review added - a gate nobody woke up red is a
decoration.

The candidate document is generated by the application's own generator, the
way CI does it:

.. code:: console

    $ docker compose -f docker-compose.yml -f docker-compose.dev.yml \
        run --rm pre-commit-check python manage.py spectacular \
        --file /opt/mrmap/openapi-candidate.json --format openapi-json

The reviewed baselines are files
================================

Three committed, human-reviewable files carry every judgement a gate applies.
The pull request that edits one of them IS the review - the tool reads the
answer, it never re-asks it and never accepts an answer at the command line.

``scripts/release_contract_baseline.json``
    The contract baseline. Two modes. **pre-baseline** (today, and the honest
    reading of #1578's measurement: 0 tags, 0 releases) declares that no
    previously supported stable release exists to diff against, and declares
    the reviewed 0.x reading standing in until one exists; a manifest claiming
    pre-baseline without that declaration fails the gate *cannot run*, because
    then nobody decided the fallback. **released** names the baseline's
    version, its source tag and the committed snapshot of its OpenAPI
    document; cutting the first stable release replaces the manifest in its
    own reviewed pull request, and from that moment ``api`` is a full contract
    diff with no mode switch of its own.

``scripts/release_contract_exceptions.json``
    The reviewed exceptions ledger. A breaking contract finding, or a
    destructive operation in a new migration, passes only when an entry names
    it and cites the issue or pull request that reviewed it (``refs``). An
    entry that matches no current finding is itself a failure - **stale
    exceptions are how a ledger starts covering changes nobody reviewed.** A
    target is matched exactly, or as a *bounded* trailing-``*`` prefix
    (``notify.0007_*``); a bare ``*`` is refused as a cannot-run, because its
    empty prefix matches everything of that kind - one reviewed entry would
    approve every future breaking change of the kind, and the stale check could
    never fire for it. The point of the ledger is that the PR editing it IS the
    review, and what a human approved there was a named change.

``scripts/release_upgrade_baseline.json``
    The staged #1180 boundaries: the oldest supported upgrade baseline (the
    release carrying #1178 and #1179, marker ``notify.0006_remove_backgroundprocess_threads``
    in ``django_migrations`` - #1180 answer 3), the migration nodes whose
    *names* stay load-bearing although #1180 emptied their bodies
    (``registry/0014``/``0020``/``0037`` parent on ``notify/0005``, and
    ``0007`` parents on ``0006``), and the retired application
    ``django_celery_results`` that may never again be named as a Django
    application. What an operator does about them stays written in
    :ref:`celery-result-backend`; this file is the machine-checkable echo, and
    prose ABOUT the retired app (as in its migration docstrings) is not a hit.

What each gate decides
======================

``api`` - the public contract
    Diffs the candidate OpenAPI/JSON:API document against the baseline
    snapshot. Breaking: removed operation or operationId, removed parameter,
    newly required parameter or request body, removed response status, removed
    property, newly required property, changed property type, narrowed enum -
    each must be covered by the ledger, each that is not fails the gate.
    Additive changes are counted, never failed. A candidate whose
    ``info.version`` is not the checkout's canonical version is refused: that
    is a stale generated file, and a stale file cannot attest a candidate.
    Everything a schema diff *cannot* see (authentication semantics, the
    meaning of a kept status code, error bodies, pagination, JSON:API side
    effects, the proxied OGC surface) is printed as a behavioral blindspot in
    every report - the release notes carry its acknowledgment, the diff
    refuses to pretend it saw what it cannot see.

``version`` - the bump and the notes
    Reads the change classes of the range from ``scripts/pr_classify`` (one
    classifier, one answer). Breaking requires a MAJOR bump - or a MINOR bump
    while major is 0 under the reviewed ``breaking_below_1_0: "minor"``
    reading of Q2 (which Q2's answer supersedes once recorded); a feature
    requires MINOR; a fix requires any movement; a candidate behind its
    baseline fails because a released version never moves backwards. Versions
    are compared by **SemVer precedence, not by splitting on dots**: build
    metadata is ignored for precedence (section 10), so a new build of the
    baseline version is not a bump, and a prerelease sorts *below* the release
    it precedes (section 11), so an rc candidate carries the version it will
    become (``0.2.0-rc.1``, the convention of ``scripts/image_release.py``)
    and not the baseline's own. The baseline itself must be a **stable**
    release: an rc announces a release instead of being one (``image_release.py``
    refuses the stable aliases for a prerelease), and the rc of 0.2.0 already
    carries the movement that 0.2.0 releases - so a prerelease in the manifest
    is a *cannot run*, not a reading of the bump. A version the pattern cannot
    read is a *cannot run* (exit 2) too, never a traceback: exit 1 means the
    gate decided against a candidate, and on an unreadable version it decided
    nothing. While no
    released baseline exists, the bump is reported as advisory - there is
    nothing to bump *from* - but the evidence a breaking change owes is not
    advisory: the UNRELEASED changelog must carry it as a ``**Breaking:**``
    line. Independently of the mode: every migration the range ADDS and every
    deployment setting the range ADDS to the required surface (a
    ``${VAR:?...}`` of the Compose files, an ``os.environ[...]`` of the
    settings - both make a deployment that does not provide them fail) must be
    named under a ``### Migration notes`` subsection of the UNRELEASED
    section. Notes about what a change demands of an operator are not
    optional documentation.

``upgrade`` - the migration surface
    Runs the graph gate of ``scripts/migration_graph_smoke.py`` unchanged (one
    leaf per app - #1157's reader, not a second one), then the static rules
    the QA containers cannot see from inside a fresh test database: the
    protected #1180 nodes still exist; the retired app is not named by any
    migration dependency or ``INSTALLED_APPS`` entry; **no fake migrations** -
    a new migration with an empty ``operations`` or a noop-only ``RunPython``
    is a node lying about the schema it changes, unless the file itself
    carries the reviewed marker ``# release-gates: empty-operations -- refs
    #<issue>`` (the marker is only for additions, so a human said yes to
    exactly that node); **no destructive changes without approval** -
    RemoveField, DeleteModel, RenameField, RemoveIndex and a DROP-ing RunSQL
    in a new migration each need a ledger entry. The gate also prints the
    directive the CI upgrade run must start from. The PostgreSQL runs
    themselves stay where they are: the QA containers already prove the fresh
    install by migrating from zero, and the upgrade-from-baseline run becomes
    runnable the moment a released baseline exists - duplicating those suites
    was the issue's explicit anti-goal.

``promote`` - the attestation
    Consumes the evidence file a promotion workflow gathers (tests, Sonar,
    dependency/vulnerability review, artifacts) plus the three gate reports,
    and refuses unless every check passed **for the candidate SHA itself**,
    both first-party images (:ref:`versioned-images`) carry a ``sha256:``
    digest, and all gates are green. The output is the attestation JSON
    binding ``(sha, version, channel)`` to that evidence - the callable
    contract #1584 promotes on and #1585/#1586 consume, and the tuple #1578's
    promotion design calls the frozen candidate identity. An attestation is an
    evidence binding, not an approval: promotion stays a human act on a
    permanent branch.

Deliberate limits, named
========================

* The tool has no credential and no write path: no tag, no publish, no label,
  no merge. ``promote`` writes one local JSON file where told to.
* ``api`` sees documents, not behaviour; the blindspot list is that gap
  written down, not a bug list. Behavioral gaps are acknowledged in the
  release notes - which is what #1581 curates and #1585 documents.
* The removed-deployment-setting direction is invisible to a static diff
  exactly when the range's own code was the last reader - which is precisely
  the case the Migration notes entry forces into the changelog.
* While Q1/Q2/Q5/Q6 of #1578 stay Pending, the version-bump and contract-diff
  halves run in pre-baseline mode; ``scripts/decisions`` recording a human
  answer, or cutting the first release, is what turns the released half on -
  not a knob an agent gets to set.
