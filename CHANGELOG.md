## [0.x.x] - UNRELEASED

### Added
- Cross-service attention list, app-bar count and dashboard card for service failures, update reviews and overdue schedules (#567).
- Alerts of a service answer which monitoring run, update job or harvesting job decided them, and the attention tab of a service links to that record (#596).
- The aside of a screen of services answers the selected service first: its states which need attention, the outcome of its last monitoring run and update job and a direct way to its screen (#597).
- Work queue card on the dashboard which counts the alerts, the update reviews and the running and failed background work of everything the user may see, and links to the list of those very records (#601).
- The capabilities document of a stored WMS or WFS publishes the dataset coupling a curator maintains in MrMap: a curated relation of a layer or feature type adds a metadata reference which points to the iso record of the linked dataset, beside the references which were imported with the document (#674).
- The step size a harvesting run requests pages with is a size a run can carry and the catalogue keeps it: a run which names no size starts from the size of its catalogue, a run which finished leaves the size it worked with there, and a size which no run can carry is answered as invalid input instead of breaking the run or the request (#691).
- A harvesting run finds the page size the catalogue answers instead of trusting a default nobody chose: the size is probed with a request which asks for no records, halved until the service answers it, and a page which is refused at the planned size asks its missing range again in halved steps down to a floor - every size used and every shrink is readable in the harvesting logs, and the request timeout grows with the page size so a slow page is not mistaken for a broken one (#694).
- A harvesting schedule which fires more often than a harvest of the catalogue takes asks for attention: the warning names the schedule and the duration the harvests which finished measured on average, is answered on the harvesting schedules of the catalogue and in the attention list, and never blocks saving such a schedule, because the duration of a harvest drifts with the remote catalogue (#693).
- The harvests a catalogue already had behind it answer how fast every page size is: a harvesting run which completed answers its records per minute beside the size it asked with, the size a harvest starts with is shown together with the throughput the runs of that catalogue measured per size and the fastest one of them, and a catalogue whose harvests never finished is shown without a recommendation instead of a made-up one (#692).
- Per layer opacity in the map viewer: the layer settings panel blends a layer between invisible and fully drawn in five percent steps, keeps the value for the viewer session, and asks for a map of its own as soon as two layers differ, so the blending of one layer never dims another; a feature layer dims its outlines, fills and point symbols together (#750).
- The map keeps its image while the time dimension of a WMS is scrubbed or played: the frame already drawn stays visible until the frame of a new selection is fetched, decoded and ready, the control names the observation the map shows while its successor is on its way, and identify asks that shown frame; the time control animates the advertised times from their first value with play/pause, four playback speeds and looping, holds its pace while a frame is on its way, steps over frames the service refuses, and stops at the end of the range unless looping was asked for (#705).
- The frames which follow a time selection are fetched before the user reaches them: while the timeline of a layer is open the viewer buffers the next advertised observations in the background and draws a buffered frame without asking the service again, at most two buffered frames are on their way at once, the frames a selection moved away from are taken back together with the requests still travelling for them, a layer whose timeline nobody opened and the image of the server default are left alone, and a buffered frame never answers a layer asked with different credentials (#705).
- The capabilities of a single layer or feature type have an url of their own - `/mrmap-proxy/wms/layer/{layer}` and `/mrmap-proxy/wfs/featuretype/{feature type}` - which the api names on the layer and on the feature type: the document is generated for every request out of the registry and advertises exactly that resource, writes what a nested layer inherits from its parents into the layer itself so the document answers it without the parents and restricts the type names a WFS advertises, so a viewer can be pointed at one element, while a wrong version, an unknown resource or an ambiguous identifier is answered with an exception report instead of a document; the inspection of a layer or feature type shows the recent changes of the inspected element alone (#676).
- The screens which list the registered layers and feature types open the element their user clicked in the map viewer: the card beside their rows names the service which owns that element and hands both to the buttons which open the service in the viewer, so the viewer shows the capabilities of the whole service with exactly the clicked layer or feature type activated - a secured service is opened with its secured document, a feature type is asked alone instead of offering every type of the service for the choice the click already made, and the operations a document of the registry advertises on another origin are asked upstream without the session of the requester (#676).
- Errors of the user's browser reach the central logs: a beacon script which the frontend image injects before the app bundle reports uncaught exceptions, unhandled rejections and failed resource loads to `/api/system/error`, an url the frontend's own nginx answers without the backend involved - the fields travel in the query string so one report is one line of a log of its own which ships with the container logs like the access log, its values arrive as they were sent, the address is bounded by a rate limit instead of by credentials, and the access and error logs of the frontend container join the log stack (#889).

### Changed
- The first boot of the web app travels lighter: the nginx of the frontend image compresses the answers it serves itself, lets the hashed files under `/assets/` be cached immutably and keeps the html uncached, and `/api/schema` answers with a strong ETag, a public cache directive and a `Vary` without credentials, so a reload of the app asks for the multi-megabyte schema document only to learn that nothing changed and downloads it in full once per cache period instead of once per boot (#946).
- The system status of the app bar stops polling `/api/system/status/current` while the MrMap tab is hidden and refreshes the displayed status as soon as the user returns (#749).
- The browsable REST API is a development facility only; a production deployment (`MRMAP_PRODUCTION=True`) registers no browsable renderer, so an HTML-only request is answered with the usual content negotiation rejection and requests without an `Accept` header receive the JSON:API representation (#751).
- A metadata reference of an imported capabilities document is published as it was imported and is removed only if the database does not know its link anymore; a reference which holds no online resource is no longer published, because it is not valid xml (#674).
- building docs with readthedocs.org instead of using custom github action to publish with github pages.
- Importing one harvested metadata record writes its row once instead of up to three times: the xml backup of the document and the reason of its history row travel with that one statement, a record which the catalogue did not change is not written at all, and a harvest no longer answers `is_customized` of a record it only re-harvested (#858).
- The import which writes harvested records to the database is bounded by chunks instead of one task per record: a harvest of 70,000 records publishes ~280 tasks (`MRMAP_HARVEST_IMPORT_BATCH_SIZE`, 250 by default) instead of 70,000 broker messages, task round-trips and result writes, and the directory import of stored files is bounded the same way; every record still commits on its own, keeps its own documented import error without failing the chunk it sits in, and is skipped as already imported when its chunk is delivered again, while the progress a harvest reports stays granular by record (#859).
- The history chart of a resource counts the changes per day of the last 30 days as stacked bars of the additions, the updates and the deletions, draws the inventory as a line above them and names the time, the unit and the resource it counts in a caption; a resource which answers no statistics, a request which is still asked and a request which failed are told apart from a resource without any change (#601).
- `scripts/agent_capacity` measures the memory of the cgroup an agent actually runs in instead of the machine's: a job is admitted against the smaller of `MemAvailable` and the headroom of its own cgroup and every parent, counting only what cannot be reclaimed, it distinguishes a heavy Compose test stack from a light agent slot, counts stacks and processes prospectively so `stacks 3 (max 3)` no longer admits a fourth, and refuses a new stack under memory pressure or at the cgroup ceiling without ever touching a running job - the 16 GiB agent container whose 11 OOM kills the 2026-11-05 diagnosis recorded is now seen as 16 GiB instead of the 63 GiB `/proc/meminfo` reports; thresholds, metrics and the measured before/after are in `docs/source/development/agent-capacity.rst` (#1053).
- The unit-test job runs its suite in four forked workers instead of one process: the 1312 tests of `tests/django` measured 655 s in a single process and 225 s with `--parallel=4` in the same stack, and the peak of the container's memory cgroup did not rise with them (12.1 against 12.5 GiB), while the worker count is written out rather than left to the runner's `cpu_count` because Django brings up one PostGIS test database per worker; `COVERAGE_FILE` and `concurrency = multiprocessing` travel with the switch because a forked worker inherits the environment of its parent but not its command line, so without either one the job uploads a coverage report that silently lacks every line only a worker executed and still exits 0 - `scripts/test_coverage_parallel_data.py` pins that together with the single-process shape of the acceptance job, and `backend/AGENTS.md` now carries the measured numbers in place of a baseline that no longer described this suite (#1055).

### Fixed
- The import progress of a harvesting job no longer stays at 0% while its metadata-file tasks complete (#958): each import task now credits the files it actually committed to the background process, coalesced into one bulk increment per ~200 files or ~30 seconds per worker (`MRMAP_HARVEST_IMPORT_PROGRESS_STEPS`, `MRMAP_HARVEST_IMPORT_PROGRESS_SECONDS`) so a 400k-record backlog reports thousands of times instead of contending on one row per file. The increment is capped at `total_steps` and only ever moves up, retried and re-published tasks credit each committed transition once (never a Celery success event), a chord rebuild reconciles lost in-flight credits from the still-present backlog without shrinking the total, and completion reports all steps as done; the harvesting API and its per-record progress annotations are unchanged.
- The provenance a harvesting run carries - `origin` and `origin_url` - now lands on the written rows of all three record types: the persistence handler resolves an import's defaults whether it keys them by record type name (`"dataset"`, `"service"`, `"application"`) or by model class name, and the single write of a record no longer `setdefault`-s them onto the column values of the parsed document which already name every empty column as `None`; a harvested record answers where it came from and from which catalogue, a republished record carries the newer of both and a dataset whose origin url a published metadata reference points at is no longer imported without one (#976).
- A periodic task which runs longer than its beat interval no longer starts a second concurrent run of itself: the singleton which keeps the instances of one task apart is the lock of the run which holds it and not of a 300 second clock, so a slow import of the stored metadata files is never overlapped by the fire which comes after it and a worker which dies leaves no lock behind (#852, #837).
- The identify query of the viewer asks every queryable layer with its own GetFeatureInfo request instead of combining the layers of one service into one query: a service may spend the FEATURE_COUNT of a combined request on its first layers and leave the later ones without an answer, which the inspector then showed as a conclusively empty layer; the layers of one service still share one map request (#700).
- A harvesting job which is redelivered while it runs - by a schedule which fires again, by a retry or by a worker restart - no longer downloads a page whose records are already stored; the page is recognised by the request which asked for it and only missing pages are requested from the remote catalogue again (#688).
- A harvesting run which could not fetch all its pages says so: a task which gave up after its retries ends the job as aborted, which the alert of the catalogue, its harvest history and the notification of the background process already answer, instead of leaving the job unfinished until a worker restart re-publishes the whole harvest; a page which the catalogue refused leaves the same trace of missing records as a page which came back short, so the run is answered as one which is not done with instead of a clean completion of a partial snapshot (#690).
- A WFS `GetCapabilities` request is answered again: the proxy converted the per feature type security information which the security manager annotates only for the requests it secures per feature type, so a capabilities request, which is not one of them, ended on the missing annotation instead of answering the service (#676).
- The fallback query of a harvesting run which asked the catalogue with the `csw:Record` type names is now the answer which gets checked, logged and retried; it was the first answer which was judged, so a broken fallback ended the run on a missing node instead of producing its log entry and its retry - and only status codes of the server error class are retried, where the comparison meant "500 or above" (#689).
- A catalogue which refuses our query with a namespace prefixed exception report - `<ows:ExceptionReport>` instead of `<ExceptionReport>` - is refused for the harvesting run too: the report is recognised by what it is and not by a substring of the document, so it is answered as the remote error of the harvesting log instead of being read for a record count which ends the whole harvest on a crash; a response document which simply carries no `SearchResults` names no records and takes the run to its log of a missing count (#815).
- The dumps which the slow request logging leaves below the media root have a bounded life and are no longer readable by anybody who guesses the url: a periodic task which beat hands over hourly takes back the dumps which are older than the configured age or beyond the configured count, instead of a deployment collecting hundreds of thousands of files in one directory until its disk is full, and the media route - the nginx of the stack and the backend behind it, for every origin it is reached from - answers that directory like an unknown file, because a dump carries complete sql statements, the internal host names which answered the request and its metadata (#888).
- The sql of a slow request dump is sql which runs: the parameters of a logged statement were rendered with the `repr` of their python values, so the statement copied out of a dump failed in psql with `ERROR: schema "datetime" does not exist` where `COALESCE(SUM(...), timedelta(0))` should have been asked, and the same false friend hid which of the aggregations were parameterized at all; a parameter now answers the literal its type answers for the database - `'0:00:00'::interval`, `'beeacc4e-…'::uuid`, `'…'::timestamptz` - and only a type the driver has no adapter for is still left with its `repr` (#887).
- The progress of a harvesting job asks the files it left behind only for the files each of its numbers is about: the count of the files which failed to import and the count of those which still wait without an error carried their condition as a `COUNT(...) FILTER` in front of the whole backlog of the job, which reads the entries of every file of the job to find the few it counts - the reported job read the entries of all 411,518 files it had left behind to answer how many of them had failed, ~200 ms of the 564 ms its detail request measured, and the same again on every poll of the job screen. Both conditions are now the range of the subquery which answers their count, and a range is what the new index over the job and its error flag answers out of the entries of the files which failed (#886).
- The harvesting overview counts its jobs without running their statistics: the paginator asked the annotated queryset for the number of rows of the answer, which materialized the aggregation of the whole table of the harvested metadata relations a second time per request - one overview of a deployment which harvested ran over 259,377 rows twice, 1,081 ms and 12,222 ms of the 14 s its slow request dump logged, because the statistics of a job are joined `LEFT OUTER` onto one aggregate row per job and cannot answer more or fewer jobs than the job table itself (#885).
- A metadata file which carries a `gmd:keyword` longer than 300 characters is imported again: ISO 19115 gives a keyword no length and a catalogue which joins its plan names into one text publishes one of 347 characters, which raised `StringDataRightTruncation` on the insert of the keyword - and the import task reads any exception of a file as a record error, so the file was marked and the records of a catalogue which never refused anything were lost. The keyword of a record and the keywords array which makes a record findable by it are text now, like the other free text of a record is, and the unique index over the keyword answers a value the storage keeps out of line, so a keyword of any length is stored and every word of it - including the ones at the end of such a joined list - stays what the record is found by (#894).

### Removed
- The in-repository agent supervisor: `scripts/agent_supervisor` with its `scripts/agent-supervisor` command, its user-level service unit `scripts/systemd/mrmap-agent-supervisor.service`, its seven offline checks (`scripts/test_agent_supervisor_*.py`) and its operator documentation. Development orchestration is external now - Agent Orchestrator starts, watches and stops the worker sessions that used to be a supervisor's ticks - while the host tooling that supervisor was built on stays and is still what any orchestrator is expected to use: `scripts/wip` for claims, `scripts/agent_capacity` for admission, the prebuilt dependency images and the per-job Compose isolation (#1102).
- The nine materialized views which held the changes of a resource per day, and with them the periodic task which rebuilt them eleven times an hour: the endpoints under `/api/registry/statistical/` answer the aggregation over the audit records of the resource themselves, so a change is counted with the request which asks for it instead of with the next rebuild, and a deployment which scheduled that rebuild loses the task and the schedule it used with the migration (#857).

### Changed
- moved axis_order_cache package to it's own repo
- Removed pycharm run configurations, cause there are outdated and the common development environment is vscode.
- migrate to docker compose cli plugin v2.x.x

## [0.1.0] - 2023-03-23
